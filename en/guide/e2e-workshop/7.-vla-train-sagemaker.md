# 7. VLA Training and Deployment Pipeline Using SageMaker

In this module, you will fine-tune the [NVIDIA GR00T N1](https://developer.nvidia.com/gr00t) VLA (Vision-Language-Action) model using AWS SageMaker. Unlike [Module 6](6.-vla-train-batch.md) (AWS Batch), SageMaker allows **immediate deployment as a real-time inference endpoint** for easy integration with robot systems.

A single SageMaker Pipeline execution **automatically progresses through training → Model Registry registration → Endpoint deployment**. The same pipeline definition can be reused by changing only parameters, and the resulting endpoint can be immediately invoked via [SageMaker Endpoint](https://docs.aws.amazon.com/sagemaker/latest/dg/realtime-endpoints.html) REST API. You can compare and verify training curves against Batch results using the same dataset (LightwheelAI/leisaac-pick-orange, SO-101 robot).

| Service | Description |
|--------|-----------|
| [Amazon SageMaker Training Job](https://docs.aws.amazon.com/sagemaker/latest/dg/train-model.html) | Managed service for training ML models in the cloud (submit training script in container, gets GPU allocation and auto-runs) |
| [Amazon SageMaker Model Registry](https://docs.aws.amazon.com/sagemaker/latest/dg/model-registry.html) | Catalog for storing, approving, and managing trained model versions |
| [Amazon SageMaker Endpoint](https://docs.aws.amazon.com/sagemaker/latest/dg/realtime-endpoints.html) | Managed hosting for serving deployed models as REST API 24/7 |
| [Amazon ECR](https://docs.aws.amazon.com/AmazonECR/latest/userguide/what-is-ecr.html) | Private Docker Hub — training/inference container image repository |
| [AWS CodeBuild](https://docs.aws.amazon.com/codebuild/latest/userguide/welcome.html) | Cloud service that automatically builds Docker images |
| [Amazon S3](https://docs.aws.amazon.com/s3/latest/userguide/Welcome.html) | Object storage for datasets, models, and checkpoints |

{% hint style="info" %}
This module assumes `infra/groot` CDK deployment is completed from [Module 5.2](5.-train-infra-setup.md#5.2-gr00t-fine-tuning-cdk-deployment). Since a single `npm run deploy -- -c userId=<userId>` from Module 5 creates all Batch + SageMaker infrastructure, this module requires no separate infrastructure deployment steps.
{% endhint %}

### Step 4. Record ECR URI in config.yaml

If built via console, `config.yaml` doesn't auto-update, so fill manually. Following block fills `ecr.training_uri`/`ecr.inference_uri` to match account/region (ECR names themselves have no per-user suffix):

```bash
export ACCOUNT_ID=$(aws sts get-caller-identity --query Account --output text)
export REGION

python - <<'PY'
import os, yaml
account = os.environ["ACCOUNT_ID"]
region  = os.environ["REGION"]
cfg = yaml.safe_load(open("config.yaml"))
cfg.setdefault("ecr", {})
cfg["ecr"]["training_uri"]  = f"{account}.dkr.ecr.{region}.amazonaws.com/groot-sm-training:latest"
cfg["ecr"]["inference_uri"] = f"{account}.dkr.ecr.{region}.amazonaws.com/groot-sm-inference:latest"
yaml.safe_dump(cfg, open("config.yaml", "w"), allow_unicode=True, default_flow_style=False)
print(cfg["ecr"])
PY
```

The later steps `run_training.py`, `deploy_endpoint.py`, and `run_pipeline.py` automatically use the ECR URI from `config.yaml`.

#### Uploading SO-101 (NEW_EMBODIMENT) modality file (required)

`LightwheelAI/leisaac-pick-orange` is a SO-101 dataset but not a built-in GR00T embodiment, so training with `NEW_EMBODIMENT`, you **must upload the modality definition file alongside the dataset to S3** so the training container correctly recognizes dimension/key mappings.

```bash
    "s3://${BUCKET}/datasets/leisaac-pick-orange/modality_config.py" \
    --region "${REGION}"
```

> For other robots/datasets, create manually referring to modality files under `training/data/configs/` (see *Preparing custom robot dataset* below). Built-in GR00T embodiments (`LIBERO_PANDA`, etc.) can skip this step.

## 7.5 Registering SageMaker Pipeline Definition (~3 minutes)

[SageMaker Pipelines](https://docs.aws.amazon.com/sagemaker/latest/dg/pipelines.html) bundles training → Model Registry registration → Endpoint deployment in one definition, then **reuses** by changing only parameters. This step creates only the definition without starting training; actual training starts in 7.6 with *Start execution*.

```mermaid
flowchart LR
    Definition["Pipeline definition\n(GR00TFinetune + RegisterModel + DeployEndpoint)"]

    Definition -->|"Start execution #1\n(Quick validation)"| Exec1
    Definition -->|"Start execution #2\n(full training 6000 steps)"| Exec2
    Definition -->|"..."| ExecN

    subgraph Exec1["Execution #1"]
        direction LR
        T1["GR00TFinetune"] --> R1["RegisterModel"]
    end
    subgraph Exec2["Execution #2"]
        direction LR
        T2["GR00TFinetune"] --> R2["RegisterModel"]
    end
    subgraph ExecN["Execution N"]
        direction LR
        TN["GR00TFinetune"] --> RN["RegisterModel"]
    end

    R1 --> Reg
    R2 --> Reg
    RN --> Reg
    Reg["Model Registry\n(version 1, 2, ..., N)"] --> EP["SageMaker Endpoint\n(latest version auto-deployed)"]
```

### Step 1. Upload training script (`sourcedir.tar.gz`) to S3

[SageMaker Script Mode](https://docs.aws.amazon.com/sagemaker/latest/dg/adapt-training-script.html) injects training scripts at runtime instead of baking into container image. Container contains only training dependencies (PyTorch, flash-attn, GR00T libraries); entrypoint script is received as separate tarball. Even after modifying `train.py`, only re-run this step without container rebuild.

```bash
cd ~/aws-physical-ai-recipes/e2e-workshop/groot

SRC_KEY="codebuild-source/sourcedir.tar.gz"
rm -f /tmp/sourcedir.tar.gz
tar -czf /tmp/sourcedir.tar.gz -C training/container train.py
aws s3 cp /tmp/sourcedir.tar.gz "s3://${BUCKET}/${SRC_KEY}" --region "${REGION}"
echo "S3 source: s3://${BUCKET}/${SRC_KEY}"
```

With Script Mode, just fix and re-upload `train.py` without rebuilding container. Container contains only training dependencies (PyTorch, flash-attn, GR00T libraries); entrypoint script loads at runtime.

### Step 2. Register Pipeline definition

[Pipeline Step](https://docs.aws.amazon.com/sagemaker/latest/dg/build-and-manage-steps.html) is a unit of work within workflow. Each Step, by **type** (Training / Processing / Model / Condition, etc.), SageMaker automatically creates and runs corresponding resources (Training Job, Processing Job, Model Package…); one Step's output (e.g., S3 path of `model.tar.gz`) naturally connects as input to next Step.

This guide's Pipeline comprises three Steps:

| Step | Type | Function |
|------|------|---------|
| `GR00TFinetune` | [TrainingStep](https://docs.aws.amazon.com/sagemaker/latest/dg/build-and-manage-steps.html#step-type-training) | Run SageMaker Training Job to fine-tune GR00T and save result as `model.tar.gz` to S3 |

## 7.9 Confirming Endpoint Auto-Deployment (~10 minutes)

`DeployEndpoint` LambdaStep automatically performs the following at pipeline end:

1. Delete existing endpoint with same name if present (wait for waiter, ~1-2 minutes)

## 7.12 Cleanup

Delete resources after workshop to reduce costs.

### 1. Delete Endpoint:

```bash
python inference/sagemaker/deploy_endpoint.py --action delete
```

Expected output:

```
Deleting endpoint: groot-sm-endpoint-yoo
Endpoint deletion in progress...
Endpoint deleted successfully
```

### 2. Clean up SageMaker Studio apps/UserProfile (before deleting per-user stack):

CloudFormation cannot delete per-user stack if active KernelGateway/JupyterServer apps or your UserProfile remain. Empty them in order below. (Studio Domain itself is shared stack owned; do not delete).

```bash
DOMAIN_ID=$(aws ssm get-parameter --name /groot-finetune/studio-domain-id \
    --query 'Parameter.Value' --output text --region "${REGION}")

# Delete all active apps in your UserProfile
aws sagemaker list-apps --domain-id-equals "${DOMAIN_ID}" --region "${REGION}" \
    --query "Apps[?UserProfileName=='${USER_ID}' && Status!='Deleted'].[AppType,AppName]" --output text | \
while read -r TYPE APP; do
    aws sagemaker delete-app --domain-id "${DOMAIN_ID}" \
        --user-profile-name "${USER_ID}" --app-type "${TYPE}" --app-name "${APP}" \
        --region "${REGION}"
done
```

> UserProfile itself is owned by per-user stack (`GrootFinetuneSagemaker-${USER_ID}`), so next step's `cdk destroy` / CFN delete automatically removes it.

### 3. Stop (or delete) MLflow tracking server:

**For temporary breaks** without deleting full stack, just stop to stop hourly charges (artifacts remain on S3, metadata preserved):

```bash
aws sagemaker stop-mlflow-tracking-server \
    --tracking-server-name "groot-mlflow-${USER_ID}" \
    --region "${REGION}"
```

MLflow server also deleted when per-user stack deleted in next step; no separate action needed.

### 4. Delete CDK stacks (your per-user stacks only):

Shared stack (`GrootFinetuneShared`) may be used by other users, so **delete only your per-user stack**.

```bash
cd ~/aws-physical-ai-recipes/e2e-workshop/infra/groot
npm run destroy -- -c userId="${USER_ID}"
```

Or directly via CloudFormation API:

```bash
aws cloudformation delete-stack \
    --stack-name "GrootFinetuneSagemaker-${USER_ID}" \
    --region "${REGION}"

# (Optional) Also clean up Batch stack
aws cloudformation delete-stack \
    --stack-name "GrootBatchTrain-${USER_ID}" \
    --region "${REGION}"
```

{% hint style="warning" %}
**ECR Repository (shared ownership):** SageMaker training/inference ECR (`groot-sm-training`, `groot-sm-inference`) are shared stack owned; other users use them. **Do not delete.** Administrator cleans up with `cdk destroy GrootFinetuneShared` after workshop.

**S3 Bucket (per-user):** Auto-empties if objects exist on stack deletion, but manual cleanup also possible:

```bash
aws s3 rm "s3://${BUCKET}" --recursive
```

{% endhint %}

## 7.13 Troubleshooting

| Symptom | Cause | Solution |
|------|------|------|
| `Access to model nvidia/Cosmos-Reason2-2B is restricted` | N1.7 used but HF_TOKEN not set or license not agreed | Agree to license on [model page](https://huggingface.co/nvidia/Cosmos-Reason2-2B) then add `--hf-token ssm:/groot/hf-token` |
| ECR authentication failure (`Unauthorized`) | AWS credentials expired or insufficient permissions | Check `aws sts get-caller-identity` then refresh credentials |
| CodeBuild build failure | flash-attn download failure, network issues | Check CloudWatch `/aws/codebuild/groot-sm-training-build` then retry |
| `Resource of type 'AWS::ECR::Repository' with identifier 'groot-sm-...' already exists` | Remnants of old split stack SM ECR remain. New unified shared stack doesn't use same name, usually doesn't occur, but if old stack operated in same account, manually delete ECR then retry `npm run deploy:shared` | `aws ecr delete-repository --repository-name groot-sm-training --force` |
| Training Job ResourceLimitExceeded | Insufficient instance quota | Request increase for "Running On-Demand ml.g6e instances" in AWS Service Quotas |
| SageMaker Training Job fails immediately | Container image missing from ECR or insufficient IAM role | Check `aws ecr describe-repositories` and IAM permissions |
| Endpoint 5xx error (`ModelInvocationTimeOut`) | model.tar.gz missing inference_metadata.json | Check Training Job logs for model save completion |
| Pipeline DeployEndpoint Step failure (`transient state` error) | Same-name EP in Creating/Updating state | Wait for EP to reach InService/Failed, then retry pipeline |
| Pipeline DeployEndpoint Step failure (`AccessDenied`) | Insufficient Lambda IAM permissions or SageMakerRole missing lambda:InvokeFunction | Rerun `cd ~/aws-physical-ai-recipes/e2e-workshop/infra/groot && npm run deploy -- -c userId=${USER_ID}` to refresh IAM, check CloudWatch `/aws/lambda/groot-deploy-endpoint-${USER_ID}` logs |
| Inference dimension mismatch (`shape mismatch`) | proprioception value count ≠ model expected value | Check correct input format (keyed or flat) and dimensions in error message, retry |
| No model.tar.gz after Training Job | Training script failed or insufficient S3 permissions | Check CloudWatch logs for training completion message and validate IAM S3 permissions |
