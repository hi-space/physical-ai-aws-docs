# 4. VLA Training Execution (GR00T Fine-tuning)

## 4.1 Training Environment Setup

This section submits GR00T VLA model fine-tuning jobs using SLURM. HyperPod automatically provisions GPU nodes and releases them after training completes.

GR00T training uses **Python virtual environment (venv) mode**. No containers required; install a shared environment on FSx once, then all nodes use it.

```bash
# Install GR00T training environment (~5-10 minutes) — default: N1.6
bash /fsx/scratch/aws-physical-ai-recipes/hyperpod-training/scripts/setup_groot_env.sh
```

This script:
- Installs system packages (`ffmpeg`, `git-lfs`)
- Installs `uv` package manager
- Clones Isaac-GR00T repository (`/fsx/scratch/Isaac-GR00T`)
- Creates Python 3.10 virtual environment (`/fsx/envs/gr00t`)
- Installs GR00T packages and dependencies (`bitsandbytes`, `flash-attn`, etc.)

<details>

<summary><strong>To use N1.7 (requires HuggingFace token)</strong></summary>

GR00T N1.7 is a **gated model** requiring additional setup. Skip this section if using N1.6 (default).

**Step 1.** Request model access on HuggingFace:

1. Visit https://huggingface.co/nvidia/GR00T-N1.7-3B → Click "Request access"
2. Visit https://huggingface.co/nvidia/Cosmos-Reason2-2B → Click "Request access"
3. Go to https://huggingface.co/settings/tokens and generate a Read token

**Step 2.** Install N1.7 environment and save token:

```bash
# Install with N1.7
GROOT_VERSION=n1.7 bash /fsx/scratch/aws-physical-ai-recipes/hyperpod-training/scripts/setup_groot_env.sh

# Save token (training scripts read it automatically)
echo "hf_xxxxxxxxxxxx" > /fsx/scratch/.hf_token
export GROOT_VERSION=n1.7
```

</details>

### Verify Installation

```bash
source /fsx/envs/gr00t/bin/activate
python -c "import gr00t; print('GR00T OK')"
python -c "import torch; print(f'PyTorch {torch.__version__}, CUDA: {torch.cuda.is_available()}')"
```

Head node (ml.m5.xlarge) has no GPU, so `CUDA: False` is normal. Compute nodes (GPU instances) show `CUDA: True`. SLURM jobs run on GPU compute nodes.

## 4.2 GR00T Fine-tuning CLI

GR00T uses the `gr00t.experiment.launch_finetune` module for fine-tuning (same for N1.6/N1.7):

```bash
# SO101 place-orange fine-tuning (single GPU)
python -m gr00t.experiment.launch_finetune \
  --base-model-path nvidia/GR00T-N1.6-3B \
  --dataset-path /fsx/datasets/groot/so101-place-orange \
  --embodiment-tag new_embodiment \
  --modality-config-path /fsx/scratch/aws-physical-ai-recipes/hyperpod-training/configs/so101_modality.py \
  --num-gpus 1 \
  --global-batch-size 32 \
  --max-steps 2000 \
  --save-steps 2000 \
  --no-use-wandb \
  --output-dir /fsx/checkpoints/vla/groot-so101-place-orange
```

**Key parameters:**

| Parameter | Description | Default |
|---------|------|--------|
| `--base-model-path` | Base model (HuggingFace repo or local path) | Required |
| `--dataset-path` | LeRobot v2 format dataset path | Required |
| `--embodiment-tag` | Robot platform tag | Required |
| `--num-gpus` | Number of GPUs to use | 1 |
| `--global-batch-size` | Global batch size | 2 |
| `--gradient-accumulation-steps` | Gradient accumulation steps | 2 |
| `--max-steps` | Maximum training steps | 10000 |
| `--save-steps` | Checkpoint save frequency | 2000 |
| `--save-total-limit` | Max checkpoints to keep | 5 |
| `--output-dir` | Checkpoint save path | ./outputs |
| `--no-use-wandb` | Disable WandB logging | - |
| `--dataloader-num-workers` | Data loading workers | 2 |

### Supported Embodiment Tags

| Tag | Robot/Dataset | Notes |
|-----|---------------|------|
| `new_embodiment` | **SO101 (this workshop)** | Requires `--modality-config-path`, 6-DOF joint position |
| `OXE_DROID_RELATIVE_EEF_RELATIVE_JOINT` | DROID dataset | Zero-shot + fine-tune |
| `LIBERO_PANDA` | LIBERO simulation | Fine-tune only |
| `XDOF` | Generic X-DOF | Zero-shot |

## 4.3 Submit SLURM Job

### Basic Training (SO101 place-orange)

```bash
# Submit training job (GR00T N1.6 + so101-place-orange)
sbatch /fsx/scratch/aws-physical-ai-recipes/hyperpod-training/slurm-templates/vla/finetune_groot_venv.sbatch
```

Default settings:
- Model: `nvidia/GR00T-N1.6-3B` (open, immediate download)
- Dataset: `/fsx/datasets/groot/so101-place-orange` (SO101 place-orange)
- Embodiment: `new_embodiment` + modality config
- GPU: 1 (L40S 48GB)
- Batch size: 32, Max steps: 2000

To use N1.7:

```bash
export GROOT_VERSION=n1.7
export HF_TOKEN="hf_xxxxxxxxxxxx"
sbatch /fsx/scratch/aws-physical-ai-recipes/hyperpod-training/slurm-templates/vla/finetune_groot_venv.sbatch
```

### Custom Configuration Training

Adjust training parameters via environment variables:

```bash
# Short test training (10 steps)
export HF_TOKEN="hf_xxxxxxxxxxxx"
export MAX_STEPS=10
export DATASET_PATH=/fsx/datasets/groot/demo_data
export EMBODIMENT_TAG=OXE_DROID_RELATIVE_EEF_RELATIVE_JOINT

sbatch /fsx/scratch/aws-physical-ai-recipes/hyperpod-training/slurm-templates/vla/finetune_groot_venv.sbatch
```

### Using run_vla.sh Wrapper (Optional)

```bash
# Submit via wrapper script
/fsx/scratch/aws-physical-ai-recipes/hyperpod-training/slurm-templates/vla/run_vla.sh \
  --model groot --dataset demo_data --max-steps 2000
```

Job submission output:

```
Submitted batch job 12345
```

When submitted, HyperPod **auto-provisions GPU nodes**. Jobs initially stay `PD(Pending)` until nodes start (takes several minutes).

### Training Environment Variables

| Variable | Default | Description |
|------|--------|------|
| `GROOT_VERSION` | n1.6 | Model version (n1.6: open, n1.7: gated) |
| `HF_TOKEN` | (N1.7 required) | HuggingFace token |
| `NUM_GPUS` | 1 | Number of GPUs |
| `DATASET` | so101-place-orange | Dataset name (under /fsx/datasets/groot/) |

| `GLOBAL_BATCH_SIZE` | 32 | Batch size |

| `SAVE_STEPS` | 2000 | Checkpoint frequency |

## 4.4 SLURM Concepts

Key SLURM commands for efficient HyperPod training job management:

### sbatch: Submit Batch Job

```bash
# Submit from script file
sbatch train_job.sh

# Submit inline
sbatch << 'EOF'
#!/bin/bash
#SBATCH --nodes=1
#SBATCH --gres=gpu:1
echo "Hello from SLURM"
EOF
```

**Common options:**

| Option | Description |
|------|------|
| `--job-name` | Job name |
| `--partition` | Job queue (HyperPod Managed: `dev`) |
| `--nodes` | Number of nodes |
| `--gres=gpu:N` | Number of GPUs (N = 1, 2, 4, 8, etc.) |
| `--time` | Max runtime (HH:MM:SS) |
| `--output` | Standard output file |
| `--error` | Standard error file |

### squeue: Check Job Queue

```bash
# View all jobs
squeue

# Check specific job
squeue -j <JOB_ID>

# View current user's jobs only
squeue -u $USER

# Real-time monitoring (refresh every 2s)
watch squeue
```

Example output:
```
             JOBID PARTITION     NAME     USER ST       TIME  NODES NODELIST(REASON)
             12345       dev groot-fi ubuntu    R    10:25      1 ip-10-0-1-42
             12346       dev test-run ubuntu    PD       0:00      1 (Priority)
```

**Status codes:**

| Status | Code | Meaning |
|------|------|------|
| Pending | PD | Waiting for GPU node provisioning |
| Running | R | Training in progress |
| Completed | CD | Success |
| Failed | F | Error |
| Cancelled | CA | User cancelled |
| Configuring | CF | Node setup in progress |

### scancel: Cancel Job

```bash
# Cancel specific job
scancel <JOB_ID>

# Cancel all user jobs
scancel -u $USER
```

### GPU Memory Monitoring

While job is running, use `srun --overlap` to run commands on compute node:

```bash
# Check GPU status on running job's node
srun --jobid=<JOB_ID> --overlap nvidia-smi

# Real-time GPU monitoring (5s refresh)
srun --jobid=<JOB_ID> --overlap watch -n 5 nvidia-smi
```

{% hint style="info" %}
HyperPod compute nodes are dynamically provisioned; direct SSH access isn't supported. Use SLURM's `srun --overlap` to send commands to running job nodes.
{% endhint %}

## 4.7 Open-loop Inference Test

Test inference accuracy of trained model against dataset. Inference requires GPU, so allocate compute node via `srun`:

```bash
# Allocate interactive GPU shell
srun --partition=dev --gres=gpu:1 --time=00:30:00 --pty bash

# Inside compute node
source /fsx/envs/gr00t/bin/activate
cd /fsx/scratch/Isaac-GR00T

python /fsx/scratch/aws-physical-ai-recipes/hyperpod-training/examples/vla/verify_in_sim.py \
  --model-path /fsx/checkpoints/vla/groot-so101-place-orange/checkpoint-2000 \
  --dataset-path /fsx/datasets/groot/so101-place-orange \
  --embodiment-tag new_embodiment \
  --modality-config-path /fsx/scratch/aws-physical-ai-recipes/hyperpod-training/configs/so101_modality.py \
  --traj-ids 0 1 2
```

{% hint style="warning" %}
Head node (ml.m5.xlarge) lacks GPU, so always allocate GPU nodes via `srun`. Running directly on head node produces `Can't initialize NVML` warnings and CPU-only inference (very slow).
{% endhint %}

**Expected output:**
```

Dataset: /fsx/datasets/groot/so101-place-orange
Embodiment: new_embodiment
```

## 4.9 Troubleshooting

| Symptom | Cause | Solution |
|------|------|----------|
| Job stuck in PD(Pending) | Insufficient GPU capacity | Wait or retry later. `ml.g6e.4xlarge` is sufficient |
| `CUDA out of memory` | Memory optimization not applied | Reduce `GLOBAL_BATCH_SIZE=1` or verify sbatch script patch |
| `OSError: gated repo` | N1.7 without HF token | Use N1.6 (default) or set `echo "hf_xxx" > /fsx/scratch/.hf_token` + `export GROOT_VERSION=n1.7` |
| `RuntimeError: No FFmpeg` | FFmpeg not installed | `sudo apt-get install -y ffmpeg` |
| Virtual env not found | setup_groot_env.sh not run | Run `bash /fsx/scratch/aws-physical-ai-recipes/hyperpod-training/scripts/setup_groot_env.sh` |
| 8-bit optimizer patch fails | bitsandbytes not installed | `source /fsx/envs/gr00t/bin/activate && pip install bitsandbytes` |
| slurmd not running | Compute node initialization incomplete | `ssh ubuntu@<node-ip> 'sudo systemctl restart slurmd'` |
| Empty log file | Node provisioning in progress | Run `scontrol show job <JOB_ID>` to check status |
| ZMQ connection refused | GR00T server not started or port mismatch | Check server logs and verify port numbers match |
